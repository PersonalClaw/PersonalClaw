# Visual-regression + a11y harness (`e2e/`)

The **safety rail** for the dashboard's look and accessibility: every change must show **zero unintended visual diff** against a captured baseline, and every route must stay **WCAG 2 AA clean** (no serious/critical axe violations). Mirrors the personalclaw.dev pattern — `@playwright/test` + `toHaveScreenshot` with **platform-qualified baselines**.

## What it covers

- **`visual.spec.ts`** — a full-page screenshot of every nav route (18) and query-param sub-view (2) × both themes (light/dark) = 40 baselines, plus the agent orb's states (Settings › Design, every phase at 20 and 64 px) in both themes, with motion and under reduced motion = 4 more, each taken with the page's clock paused so a moving orb is the same frame every run, plus, under reduced motion, the six routes the motion audit touched (Home, Chat, Projects, Tasks, Store, Settings) and the command palette and the composer's + menu open, in both themes = 16 more (`REDUCED_MOTION_SHOTS` in `routes.ts`, held to `docs/design/motion.md` §10 by `reducedMotionSnapshots.test.ts`). Then every route again in both themes at each of `routes.ts`'s `VISUAL_AXES`: the 390 px compact width, 200% text zoom and high contrast (forced colours with `prefers-contrast: more`), each named `<id>-<theme>-<axis>`. Reduced motion was measured as a fourth and dropped, since it matched the default on every route. Baselines live in `e2e/__screenshots__/` (committed), and every one is `-linux`: they are made and compared against the pinned image's browser alone (`e2e/visual-image.json`, `e2e/run-pinned.mjs`, #3943), with the environment they were made in recorded in `e2e/visual-environment.json`.
- **`surfaces.spec.ts`** — the UI quality check (#3941): every route, settings panel, sub-view, substate URL and opened surface in `routes.ts` and `OPENERS`, loaded **once per theme**, with the whole matrix run on that one visit as named steps — axe (`wcag2a/2aa/21a/21aa`, serious/critical block), the non-axe detectors, the accessibility tree against `__aria__/`, reduced motion, 200% text zoom, keyboard-only operation, focus order, rendered contrast of each focus ring, overflow at 1440/1024/768/412/390/320 px and 44 px targets at the four compact widths. Findings main already had live per surface and theme in `__ui-baselines__/` (shrink-only, self-clearing). A read whose answer is outside the run is answered with a fixed body (`STUBBED_READS`, `stubbedReads.ts`). A page that reads the clock (a day group, an age, a week) runs under a fixed one (`FIXED_CLOCK`), with what it lists fixed against it, so a run that crosses midnight reads the same tree. The Store's catalogue is a snapshot, `fixtures/app-catalog.json`, because the live read lists the app registry as another repository leaves it. Re-take it when the Store's cards change, never to follow the registry. Both sets are named per platform as the screenshots are, and only the `-linux` set is committed, because the tree and the findings carry what the machine decides: its platform copy, Docker and keychain support, and how its fonts render at 200% and in contrast (#3905). It is made where the screenshots are, by the Refresh visual baselines workflow, and a reviewer reads its artifact as a diff. `surfaceMatrix.control.spec.ts` plants one defect of each kind and requires each under its own step, in both themes; `assert-no-route-skips.mjs` holds the report to one whole scan per declared route and theme.
- **`idleCost.spec.ts`** — the UI quality check's idle-cost probe (#3811): Home and Chat with the default identity, the window focused and no turn running, measured over 5 s by `idleCost.ts`. No `requestAnimationFrame` call at all, and no timer or request (fetch, XHR, beacon, socket send, event stream) that recurs more than once a second, each counted by the line or the path it comes from. A window in which the gateway pushed something to the page, or a turn ran anywhere, is thrown away and measured again (up to 4), and so is a Home window that holds no answer of its 8 s loops poll; a run that never gets an idle one fails. Its controls: the wave backdrop's frame loop on Chat, and a planted frame loop, 100 ms interval and 200 ms poll on Home, each reported by name; `src/design/idleCostProbe.test.ts` holds the probe on a page of fakes.
- **`a11y.spec.ts`** — axe and the detectors over the chat Session Map's two states that need a scripted turn (the mobile drawer and the open desktop rail), which no route visit reaches.
- **`buddyPlayground.spec.ts`** — the buddy playground's scripted day (#3892), stepped end to end on `#/buddy/playground?tab=day` with the stage saved after every step in seven legs: light and dark, 320, 390 and 412 px, high contrast (forced colours and more contrast) and 200% text zoom, each step with an overflow and cut-off-text check; and every expanded card on `?tab=card` (#3893) in light, dark and reduced motion and at 320, 390 and 412 px, with the same check. The screenshots are a recording in the test's output folder, never compared, so the spec is not platform-bound.
- **`routes.ts`** — the single source of truth for the route list (mirror of `src/app/App.tsx` NAV). Add a route here and it's snapshotted + axe-scanned automatically.
- **`helpers.ts`** — `seedTheme` (seeds `localStorage['mode']` + `prefers-color-scheme` before boot), `gotoRoute` (waits for fonts + settle), `expectRouteScreenshot`.

## Auth: the harness starts its own onboarded gateway

The built SPA gates its first render on an authenticated identity/config fetch. With **no gateway** it cannot resolve identity and renders the **onboarding screen** for every route: no `NavRail`, no page content, no ⌘K listener. axe finds nothing serious/critical there — byte-identical to a genuinely clean route. That is how 96 route scans reported a pass while visiting a surface no user ever sees, and why the only test that noticed (`command palette [opened]`) failed on its mounted-ness floor while naming the *palette*.

So `playwright.config.ts` runs **two** web servers, and needs nothing configured by hand:

1. **the gateway** — `PERSONALCLAW_HOME` (and `PERSONALCLAW_WORKSPACE`, which `PERSONALCLAW_HOME` does *not* confine) in a home of the run's own, made with `mkdtemp` under the OS temp dir and removed when the run ends, never `~/.personalclaw` and never a folder another run could be using (`runPlaces.ts`). `dashboard.user_name` is pre-seeded into `config.json` because `onboarded` is **derived** from a non-empty *server-side* name — that skips the onboarding hijack with no PUT, so no CSRF/origin dance. Readiness is the `PERSONALCLAW_READY:` line, whose token Playwright's `wait.stdout` capture group hands to `auth.setup.ts` as `PW_TOKEN`.
2. **the preview server** — `PERSONALCLAW_PORT` points its `/api` proxy at that gateway.

**Auth stays ON.** No `PERSONALCLAW_AUTH_MODE=none`: that flag swaps `csrf_middleware` for `_dev_user_middleware`, so an a11y/CSRF-adjacent finding made under it would not describe a real user. `auth.setup.ts` performs the gateway's real `/?token=` handshake through the preview origin (`vite.config.ts`'s token-proxy plugin relays the `Set-Cookie`), asserts the **shell** mounted, and writes the cookie jar every spec reuses.

The cookie jar lives in a folder of the run's own BESIDE its home (`sign-in-for-<home>/state.json`, handed to `auth.setup.ts` as `STORAGE_STATE`), made 0700 because it holds a live owner token, and removed with the home; two runs never sign each other's specs out. It is not in the home because the gateway's Doctor audits the home's state paths, and a `.auth/` folder there is one no snapshot claims: every run read Settings' Doctor card as "durability degraded". A run that cannot make the folder fails before any server starts. A run with no home of its own (`PW_NO_SERVER=1`) keeps it at `e2e/.auth/`, which is gitignored (it holds a live token). To drive an **already-running** gateway instead, start one on a scratch `PERSONALCLAW_HOME` and a port of its own (never your install's: the suite drives real turns and writes the home it reaches), then pass that port and the token from its `PERSONALCLAW_READY:` line:

```bash
PW_TOKEN=<its owner token> PW_NO_SERVER=1 PW_BASE_URL=http://localhost:<its port> npm run e2e
```

The gateway's `HOME` is a folder of the run's own too, beside its home (`user-home-for-<home>/`, made and removed with it), and every variable that names a folder outside the home (`GATEWAY_UNSET` in `runPlaces.ts`: the other agent tools' setup folders, the Hugging Face and XDG folders, and PersonalClaw's own folder overrides) is taken out of its environment before it starts. Without that, whatever the gateway finds through the home folder was the machine's: at every start it lists the shared skills folder in the real home, and Settings › Security named the real folders of the machine that ran the suite. Beside the home rather than in it, for the cookie jar's reason. Every credential-shaped variable is taken out too: each name the gateway's secrets read calls a credential (`GATEWAY_CREDENTIAL_HINTS` and `GATEWAY_CREDENTIAL_WORD_HINTS`, the read's own hints), and `SSH_AUTH_SOCK` by name. Without that, Settings › Secrets listed the tokens and agent socket of whoever started the run as inherited from the host, so it read differently on every machine; now it reads "No secrets yet". A credential-shaped name no shell can unset fails the run, named, before the gateway starts. `tests/rails/test_e2e_gateway_home_is_the_runs_tree.py` runs the harness's own environment, holds every one of those folders to the run's places, and plants credential-shaped variables that the secrets read must not see.

Two failure modes this closes, both of which read as success:

- **The shell floor.** `helpers.assertShellMounted` (called from `gotoRoute`, so visual *and* a11y get it) fails the test when `nav[data-tour="rail"]` is absent. A full-screen route in the manifest (`FULL_SCREEN_ROUTES` in `routes.ts`, the buddy playground) has no rail, so its page's own `data-full-screen` mark stands in for it; the shell renders one only once the owner is onboarded, so the mark proves the same thing. The rail renders only once the server reports a name, so it proves reachable + authenticated + onboarded in one assertion. `auth.setup.ts` asserts the same thing — its old `#root.innerHTML.length > 100` check *passed* on the onboarding screen, i.e. on precisely the state it existed to prevent.
- **Skips that state their reason.** An opener returns `true` or `{ skip: <why> }`. "no list rows on this route", "no contenteditable composer", and "app shell not mounted" need different next actions from whoever reads the report; one hardcoded "no seeded data" message could not tell them apart.

## One run, three ways to share the gateway

The harness builds nothing. It serves the `web/dist` that `make web-build` (or CI's `web-build` job) built and stamped, and the preview refuses a dist whose stamp does not match the checked-out sources (`scripts/spa_dist_freshness.py check --require-stamp`), so a stale or unstamped build fails before any test runs. Every spec but the visual rail and the specs that run alone (below) runs in one invocation, `npx playwright test --grep-invert @visual`, in this order:

1. **`smoke`** — `smoke.spec.ts`, the render smoke: the built bundle mounts on six routes with every `/api` call answered in the page, so it reaches no gateway. Its planted render crash, widget catch and uncaught error must each be caught. The local pre-push gate runs this project alone: `PW_ONLY_SMOKE=1 npx playwright test --project=smoke --no-deps`.
2. **`chromium`** — every spec `isolation.ts` calls *shared*, in parallel against the one gateway and home.
3. **`stateful`** — the specs `isolation.ts` calls *serial* (`staleWrite`, `deployedArtifacts`: each writes what other specs read), one worker, after the shared project has finished whatever it answered. Then **`stateful-again-1`** and **`stateful-again-2`** run them once more in an order drawn from a seed: `PW_STATEFUL_SEED` when set, so a run can be replayed, otherwise a random one.

**A spec that measures the home runs alone** (`alone` in `isolation.ts`, #3905): the UI quality matrix and its control (the `matrix` home), and the idle-cost probe (the `idle` home), each in an invocation of its own, on a gateway and home that invocation made, as the visual rail does. In the shared project the matrix measured the threads and chats the other specs left, against baselines taken on a home nothing else wrote to, and the idle-cost probe's windows met their turns. A home's project is in the config only when the file filter names that home's specs and nothing else (`npm run e2e:ui` runs each so); `chromium` never runs them, and a filter that names one beside another spec is refused before a server starts.

**One timezone.** The gateway's `TZ` and the browser's `timezoneId` are both `RUN_TIMEZONE` (`Etc/UTC`, `runPlaces.ts`), so a time on a surface reads the same on a Mac and on CI; `src/design/e2eTimezone.test.ts` names a spec that sets its own.

Each pass starts only once the one before it has ended. A run that names only the stateful specs chains the passes by dependencies, so a red pass skips the ones after it; a full run makes each pass the teardown of a project further out (`chromium`, `setup`, then the empty `stateful-anchor`), so the stateful set runs whatever the shared specs answered. `playwright.config.ts` says why each shape is the only one Playwright allows where it is used.

Every test in the report carries an `isolation` annotation (its mode and why), every second-pass test a `stateful-seed` annotation, and the run's `metadata` carries the seed and the order. `isolationReporter.ts` fails a run in which a spec runs in a project its mode does not allow, or a home of its own shares the run with another project, or in which a test never ran (a project it needs failed, or the run stopped first), and `playwright.config.ts` refuses to load when a spec has no mode at all; `src/design/e2eIsolation.test.ts` holds each to a planted violation, the passes' order and a red first pass on the real projects among them. A new spec is classified in `isolation.ts` before it can run.

### On CI: two shards and the runs on homes of their own, merged

CI splits the browser run over three jobs. Each **`e2e-shard`** leg runs half of `smoke` and `chromium` (`--shard=N/2`, with `PW_STATEFUL_CHAIN=0`, so no stateful project), then one run on a gateway and home of its own, through `e2e/on-shard.mjs`: shard 1 the `idle` home, shard 2 the two stateful specs named, so it runs `setup`, the first pass and the seeded second pass. **`e2e-pinned`** makes two runs against the pinned image's browser (`e2e/run-pinned.mjs`, #3943): the `matrix` home, then the visual rail. Each run leaves one blob report (`shard-1`, `shard-2`, `idle`, `stateful`, `matrix`, `visual`). The **`e2e`** job merges them and judges the merged report as one run:

- `merge-legs.mjs` refuses to merge when a leg left no blob (or two), naming the leg: a leg that never ran or never finished is a red, not a smaller report. It writes the seed and order the second pass ran in over the metadata, which Playwright's merge takes from one blob.
- `assert-no-route-skips.mjs`, as before.
- `assert-one-run.mjs` holds the merged report to one run: no failure, and no error outside a test (a leg whose gateway never booted leaves only its error); every test ran (a result that passed, failed or timed out, or a skip the test made itself; an interrupted result is not a run), each leg's auth setup included; every test ran once (the setup aside: each leg runs its own), each where its isolation mode allows, the stateful set and its second pass both there under one seed, and each pass started after the one before it had ended, read from the results' own timings. A test that passed only on its retry is named with the leg run that ran it, not red: under CI it fails its leg (`failOnFlakyTests`), whose record holds the rerun alone the verdict's flake rule judges it by. `src/design/e2eMergedRun.test.ts` plants each way the merged report can be wrong.
- Each leg's own result is the run's verdict's, not a step of `e2e`'s: it reads each leg's record, so a leg that failed, was cancelled, was skipped or left no record is red there, whatever its blob held (ci.yml's `e2e` read each leg's result itself until #3915). `tests/rails/test_e2e_specs_are_executed_tree.py` holds `e2e` and `ui-quality` to running after every leg.

Beside `e2e`, the **`ui-quality`** job is the one named UI quality check (#3941, #3811). It merges the same blobs (Node only, no browser), then runs three steps, each whatever the one before it answered, so one red run names everything that failed:

- the raw-control ratchet, `npm run ui:ratchet` (`src/design/primitiveAdoption.test.ts`);
- the design detector, `npm run design:detect`, against `design-detector.baseline.jsonl`;
- `ui-quality-report.mjs`, the matrix's verdict: one line per surface and theme that failed, naming every step that failed on it (`✗ UI quality: dark theme › Chat (#/chat): axe; 44 px targets at 390px`), and a `::error` annotation for each. A flaky surface passes and is named, and so is each skipped one. A report with no `@ui-quality` test fails, and so does one whose every `@ui-quality` test was skipped, since nothing was measured. `src/design/uiQualityReport.test.ts` plants each case.

Whether the check is required on pull requests is a branch-protection setting the owner decides (#3907, #4585).

## Commands (run from `web/`)

| Command | What it does |
|---|---|
| `npm run e2e` | Everything, as **four** invocations: the non-visual specs, the matrix and the idle-cost probe each on a home of its own, then the visual rail on its own fresh gateway — **must be zero-diff / zero serious-critical** |
| `npm run e2e:visual` | Visual regression only, against the pinned image's browser (`e2e/run-pinned.mjs`). A host that is not linux/amd64 is refused, with where the runs happen |
| `npm run e2e:ui` | The UI quality check's browser matrix only (`surfaces.spec.ts` and its control, then the idle-cost probe, each on a home of its own); The Refresh visual baselines workflow rewrites the matrix's baselines. Its other two parts are `npm run ui:ratchet` and `npm run design:detect` |
| `npm run e2e:a11y` | The Session Map axe scans only |
| `npm run e2e:update` | **Regenerate** the visual baselines against the pinned image's browser, visual-only, INTENTIONALLY, when a real visual change is expected. On linux/amd64 only; everywhere else, and for every automated contributor, the Refresh visual baselines workflow is the way |
| `npm run e2e:report` | Open the last HTML report |

First-time setup on a fresh machine/CI: `npx playwright install chromium`.

## The workflow

1. **Before touching a surface**, ensure its baseline exists (`npm run e2e:visual` green).
2. Make the change.
3. `npm run e2e` — expect **zero diff**. If a change forces a **real** visual change: implement it, dispatch the Refresh visual baselines workflow (`.github/workflows/visual-baselines.yml`) on the branch, read the files its summary lists as changed and each diff in its `visual-baselines` artifact, commit the intended ones with the manifest, and **say in the change's description which baselines moved and why, in light and dark**, so review sees it. Never silently keep or revert a visual change.
4. A surface that draws something the run does not decide (the day, the run's own counts and readings, a probe's timing, a caret) is pinned before its shot, never absorbed by the tolerance: a route in `fixedClock.ts`'s `FIXED_CLOCK` loads under its instant (the UI matrix reads the same table), a read in `visual.spec.ts`'s `VISUAL_STUBS` answers with fixed values from `stubbedReads.ts` and must answer by the shot, a read in `ANSWERED` is waited for, and under forced colours a focused text field is blurred. The spec's "each pin holds" tests plant each.

## Notes

- The harness serves the built app via `vite preview` (it builds nothing: run `make web-build` first), proxying `/api` to the gateway it starts (`PERSONALCLAW_PORT`). Data-backed routes still render their **empty** state — the gateway's home is fresh — which is a valid baseline: we guard *chrome*, not data. What is **not** a valid baseline is the onboarding screen, which is what "no gateway" actually produced.
- **That "fresh home" is true at BOOT, not for the whole run — which is why the visual rail gets its own invocation.** Each `playwright test` gets a new, empty home, but `a11y`, `chat` and `sessionMap` drive **real** scripted turns into the one gateway every spec shares, and a turn writes flywheel state twice over (`context.py` records an allocation sample per ambient render; `controller.py` calls `run_end.capture()` at run end). `#/learning` reads both back, so it renders "not measured yet" before any turn and live numbers after one — and `fullyParallel` decides which side a mixed run captures. Visual-only is 40/40 zero-diff; a mixed run reds `learning-light`/`learning-dark` at ~14,900 px each. So `e2e` and `e2e:update` both run `visual.spec.ts` alone (selected by its `@visual` tag), `helpers.assertPristineFlywheel` refuses to compare pixels if that contract is bypassed, and `src/design/visualRailInvocation.test.ts` keeps the two scripts honest. Raising the pixel tolerance was never an option here: the two renderings are different **content**.
- **Each run has a home and two ports of its own**, so two runs on one machine never meet. The first load of the config makes the home and picks a free port for each server, then hands all three on as `PW_E2E_HOME`, `PW_PORT` and `PW_GATEWAY_PORT`, so the workers, the servers and the specs read the same ones. Each run also writes its output to a folder of its own, `test-results/run-<random>/` (`PW_OUTPUT_DIR`), so it clears only its own output when it starts, and CI still uploads everything under `test-results/`; a run folder left empty is removed when the run ends. The run's `metadata` records them (`e2eHome`, `previewPort`, `gatewayPort`, `storageState`). `PW_PORT` and `PW_GATEWAY_PORT` name a port instead of a free one; neither may be your install's port, so the harness can never drive your real install. `PW_E2E_HOME` names an existing home instead, which the run then leaves in place.
- The harness never reuses a server it did not start. `PW_REUSE_SERVER=1` lets it reuse a preview already answering on `PW_PORT`. `PW_NO_SERVER=1` skips both built-in servers (use an already-running pair). `PW_BASE_URL` points at an external server; `STORAGE_STATE` at an existing cookie jar; `PW_OUTPUT_DIR` at an output folder of your choosing.
- The gateway is launched with `../.venv/bin/personalclaw` when that exists, else `personalclaw` from `PATH`. With neither, the run fails loudly on the webServer — it does **not** fall back to a backendless SPA.
- Screenshots disable animations; `seedTheme` runs before app boot so there's no theme-flash in the capture.
