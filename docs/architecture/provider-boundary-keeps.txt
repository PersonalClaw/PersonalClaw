# Provider-boundary keeps — the machine-checked allowlist of DELIBERATE vendor
# residue in core. Each line is a core file
# that the residue-sweep test (tests/test_provider_boundary_residue.py) would
# otherwise flag for a vendor SDK import or a vendor credential-key / secret-detection
# literal, plus a one-line judgment for why it stays. This file IS the keeps table — the
# test fails if a listed file no longer contains a marker (stale entry) or if a marker appears
# in a file NOT listed here (un-approved regrowth). See docs/architecture/provider-boundary.md.
#
# #3500: until the sweep's vendor set was widened it knew only the channel SDKs, so the
# four OpenAI-protocol clients below — rows 1–2 of the architecture doc's judgment table,
# eight `import openai` statements — were DECLARED exceptions that nothing enforced, and
# the sweep was green on a tree it could not see. Adding them here is what turns those two
# declared rows into an enforced allowlist: a ninth vendor SDK import, in a module the doc
# does not cover, now goes red. It does NOT relocate anything — that is roadmap work, and
# this table is the baseline it would move against.
#
# NOT listed, deliberately: llm/anthropic.py. Row 1 names it beside llm/openai.py, but it
# imports no SDK (it speaks the Anthropic message format over httpx), so it carries no
# marker and the stale-entry rail would reject an entry for it. A keep is a record of
# residue that EXISTS, not of an exception that was granted.
#
# Format: <repo-relative path> — <judgment>
#
# A second kind of keep is marked `format:` (the section at the end). Those files carry no
# vendor SDK import and no credential literal, so the residue sweep never sees them; they know
# another agent tool's file layout so that its setup can be imported or PersonalClaw's agents
# exported into it. The rail checks each one exists, carries no residue, and is named in the
# "Interoperability formats" row of the architecture doc's judgment table.
#
src/personalclaw/config/loader.py — the CRED_SLACK_* credential-store KEY NAMES ("SLACK_APP_TOKEN", …) existing installs already hold; the loader is the credential store's home (bottom layer, below all apps). Renaming breaks existing installs for zero gain. Re-exported to apps via sdk/channel.py.
src/personalclaw/config/safety.py — NOT a credential key: one "SLACK_BOT_TOKEN" inside SandboxConfig.env_passthrough's `_meta` HELP TEXT, as the example of a name an operator might legitimately let a child inherit. The sweep's own comment says it targets literals "NOT plain vendor words in prose", but SLACK_[A-Z_]*TOKEN cannot tell the two apart, so the judgment is recorded here. It arrived when SandboxConfig moved out of config/loader.py (a keep above) — the residue did not change, its file did. Deliberately NOT reworded: `_meta` help strings are rendered into the config JSON schema, so editing this sentence would be observable config-schema drift.
src/personalclaw/sdk/channel.py — re-exports the CRED_SLACK_* key names from config/loader as the app-facing surface, so the slack app imports them via the SDK (no inverted import direction).
src/personalclaw/sandbox.py — the SLACK_* env-var denylist: credential env vars (SLACK_BOT_TOKEN/APP_TOKEN/USER_TOKEN) that must never reach a sandboxed child. Secret-detection data; renaming breaks the control.
src/personalclaw/security.py — the xox[bpas]- token-detection regexes and the incoming-webhook URL shapes (Slack, Discord, Teams, `hooks.` hosts): secret-DETECTION data that redacts/blocks leaked credentials. Renaming breaks the control.
src/personalclaw/workflows/secrets.py — the inline-credential lint's token SHAPE regexes (sk-/sk-ant-/ghp_/gho_/github_pat_/hf_/xox[baprs]-/AKIA/AIza/JWT/PEM): the ONE credential-shape list in the workflows package, which validator.py's save-time lint now reads instead of keeping a second copy. Same class as security.py's xox[bpas]- regexes — recognizing a vendor's key SHAPE is secret-DETECTION data, not vendor logic, and narrowing the list would silently stop catching those providers' keys.
src/personalclaw/llm/openai.py — ROW 1 of the judgment table: a WIRE-PROTOCOL client only, lazily importing the `openai` SDK twice (a stream-options 400 retry and the non-streaming path) to read its typed error classes. The /v1/chat/completions shape is a de-facto multi-vendor protocol, the SDK is NOT a core dependency (pyproject's `[openai]` extra + the openai-models app's pythonDependencies install it; MissingSDKError names the remedy when absent), and this module calls no `register_type` at import — `apps/openai-models/provider.py` decides the client is USED. Core ships the client; an app decides it runs.
src/personalclaw/stt/openai_provider.py — ROW 2: an OpenAI-*compatible* `/v1/audio/transcriptions` client. Same lazy-import contract as llm/openai.py (one importability probe in `is_available`, one in `transcribe`), and the vendor CATALOG — which model ids exist — is contributed by `apps/openai-models` through the media_catalogs.py seam, not held here. Remote inference only: no LocalModelProvider surface, so nothing vendor-specific about download/delete lands in core.
src/personalclaw/tts/openai_provider.py — ROW 2: the `/v1/audio/speech` half of the same OpenAI-compatible media protocol, with the same two lazy imports and the same app-contributed catalog. Listed separately rather than folded into stt because the keeps table is a per-FILE mirror of measured residue, and a per-directory entry could not detect a clean file going stale.
src/personalclaw/image_gen/openai_provider.py — ROW 2: the `/v1/images` half. Same protocol judgment, same two lazy imports, same app-owned catalog. Together with the two above this is the whole `stt/`, `tts/`, `image_gen/` `openai_provider.py` row the architecture doc states once.
#
# ── Interoperability formats ─────────────────────────────────────────────────────────────
format: src/personalclaw/onboarding_import/registry.py — the list of agent tools whose setup and history PersonalClaw can import, each a source module below. A registry of file layouts: no account, no network call, nothing of the other tool runs.
format: src/personalclaw/onboarding_import/sources/claude_code.py — where Claude Code keeps its setup (`$CLAUDE_CONFIG_DIR`, else `~/.claude`) and how its instructions, memory, MCP servers, skills, agents, commands and conversations are laid out, read through the importer's floors (onboarding_import/floors.py): credential-bearing paths are never opened, secrets in text are counted and dropped.
format: src/personalclaw/onboarding_import/sources/codex.py — the same for Codex (`$CODEX_HOME`, else `~/.codex`): its instructions, memories, MCP servers (config.toml), skills, agents, prompts, refused commands and conversations, read through the same floors.
format: src/personalclaw/mcp_discovery.py — offers the MCP servers another tool has configured for import, through the two source modules above, and reads a tool's files only when the owner asks for that tool or has allowed it in Settings; nothing found there is loaded without that import.
format: src/personalclaw/packs/external_formats.py — renders PersonalClaw's agents into other tools' file formats, behind a confirmed destination, contained paths, the outbound secret scan, and a never-overwrite rule for any file PersonalClaw did not write.
format: src/personalclaw/dashboard/handlers/agent_export.py — the route that exports agents into Claude Code's agents folder, thin over packs/external_formats.py; the folder is worked out from `$CLAUDE_CONFIG_DIR` as Claude Code does, never taken from the request.
format: src/personalclaw/dashboard/handlers/mcp.py — keeps MCP servers in step with Claude Code's own global config when that agent is in use; a config that exists and cannot be read is refused rather than replaced (ConfigUnreadable).
