# T1.example-config-field — a worked task-spec example

This is a **reference task spec**, not a live task: it exists so a coding agent can see the
shape of a well-formed task spec and so `python -m harness explain T1.example-config-field`
has something to demonstrate. It encodes the [[config-four-points]] rule as its governing
invariant and carries the mandatory **negative acceptance** clauses that half prose LEDGER
entries always drop — the three ways a config field silently misbehaves.

Real task specs replace this: one per fix/feature, `id` = the roadmap task id (e.g.
`T2.3`), `scenario` pointing at the triage playbook when one applies.
